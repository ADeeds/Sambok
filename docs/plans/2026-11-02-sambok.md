# Sambok Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A full-screen dog-mode display that turns on Utility Mode, shows the cabin temperature and an estimated time left, and warns by colour when the cabin gets warm.

**Architecture:** One Android app calling the car's binder services through the NEMESIS root channel. All decision logic lives in plain Java classes with host-runnable tests; the Activity only paints what those classes produce. No resident service, no lock control, no writes on launch.

**Tech Stack:** Android 4.4.2 (API 19), Java 7 source, `aapt` + legacy `dx`, v1 signing, NEMESIS package, host `javac`/`java` for tests.

**Spec:** `docs/specs/2026-11-02-sambok-design.md`

## Global Constraints

- Target Gen5W `S5W_M`, API 19, `NEEV23.USA.0000.V015.012.260507`. Firmware gate values are recorded from the unit in Task 1.
- On-device shell is `/system/bin/sh` (toolbox): no `awk`, no `busybox`, no `sed -i`. Anything Sambok runs goes through `/system/xbin/nemesis root -c`.
- The app writes exactly one car setting: Utility Mode. It must never lock, unlock, roll windows, or touch anything else.
- Opening the app writes nothing; the Utility Mode toggle is the only write, behind an explicit tap.
- Units follow the car (`IDATCService.isUnitCelsius` = 6). Thresholds are stored in °C: 29.44 and 37.78, rendered by the display rule.
- Colour is decided from the rounded displayed value, never from the raw source unit.
- An unreadable temperature shows `—` and forces amber; an unreadable countdown shows `—` only.
- LF endings on every source file; APK builds with `aapt` + `dx` at API 19 and is v1-signed.

## Review Focus

1. Palm/hand over the toggle triggering a Utility Mode write on an accidental touch — the app must not write without a completed tap. (Task 5)
2. Utility Mode reported on but the climate not actually running — the screen must not claim comfort without the state readback. (Task 4, Task 5)
3. A frozen UI when a car call hangs — the driver is outside; the screen must keep painting. (Task 5)
4. Unit switching mid-session (car set to metric while running) — the colour must match the number on the same frame. (Task 2)
5. A countdown of `0` or a negative remainder — must read `0`, not `-1 h`. (Task 3)

### Task 2: Units, thresholds and panel state

**Files:**
- Create: `src/pure/Units.java`, `src/pure/Panel.java`, `tests/run.sh`, `tests/UnitsTest.java`, `tests/PanelTest.java`

**Interfaces:**
- Produces:
  - `Units.display(double celsius, boolean isCelsius) → int` — rounded whole-degree display value.
  - `Units.format(int value, boolean isCelsius) → String` — `"21°C"` / `"70°F"`.
  - `Panel.state(double celsius, boolean isCelsius) → PanelState` — `CALM`, `WARM`, `HOT`, or `UNKNOWN` when the reading is `NaN`.
  - `Panel.strip(boolean utilityOn, boolean tempKnown) → boolean` — the amber strip.

- [ ] **Step 1: Write the failing tests**

```java
// UnitsTest
t("21C shows 21", Units.display(21.0, true), 21);
t("21C shows 70F", Units.display(21.0, false), 70);
t("29.44C is 85F", Units.display(29.44, false), 85);
t("29.4C displays 85F", Units.display(29.4, false), 85);
t("29.3C displays 85F", Units.display(29.3, false), 85);

// PanelTest — colour follows the displayed number
t("84F is calm",      Panel.state(Units.celsiusFor(84, false), false), Panel.State.CALM);
t("85F is warm",      Panel.state(Units.celsiusFor(85, false), false), Panel.State.WARM);
t("100F is hot",      Panel.state(Units.celsiusFor(100, false), false), Panel.State.HOT);
t("29C metric warm",  Panel.state(Units.celsiusFor(29, true), true),   Panel.State.WARM);
t("NaN is unknown",   Panel.state(Double.NaN, true),                   Panel.State.UNKNOWN);
t("strip on drop",    Panel.strip(false, true),                        true);
t("strip on unknown", Panel.strip(true, false),                        true);
t("no strip calm",    Panel.strip(true, true),                         false);
```

- [ ] **Step 2: Run tests to verify they fail**

Run: `sh tests/run.sh`
Expected: FAIL, `Units` not found.

- [ ] **Step 3: Implement `Units` and `Panel`**

`celsiusFor(int displayed, boolean isCelsius)` is the test-side inverse used above. `Panel.state` converts to the displayed unit, rounds, and compares against 29.44/37.78 °C expressed in that unit, so the colour and the number can never disagree.

### Task 3: The countdown

**Files:**
- Create: `src/pure/Countdown.java`, `tests/CountdownTest.java`

**Interfaces:**
- Produces:
  - `Countdown.sample(double drawKw)` — appends a sample.
  - `Countdown.remainingMinutes(double socPercent, double cutoffPercent, double capacityKwh) → int` — `-1` when an input is unknown, `0` when the remainder is zero or negative, and the smoothed estimate otherwise.
  - `Countdown.format(int minutes) → String` — `"≈ 6 h 20 m"`, `"> 1 day"`, `"0"`, `"—"`.

- [ ] **Step 1: Write the failing tests**

```java
t("one hour",        Countdown.format(60),                       "≈ 1 h 0 m");
t("ten min rounding",Countdown.format(70),                       "≈ 1 h 10 m");
t("over a day",      Countdown.format(1500),                     "> 1 day");
t("zero",            Countdown.format(0),                        "0");
t("unknown",         Countdown.format(-1),                       "—");
t("no samples",      Countdown.remainingMinutes(80, 20, 77.4),   -1);
```

Plus a smoothing test: three samples of 1 kW then three of 3 kW must land between the two, not at either end.

- [ ] **Step 2: Run tests to verify they fail**

Run: `sh tests/run.sh`
Expected: FAIL, `Countdown` not found.

- [ ] **Step 3: Implement `Countdown`**

Rolling mean over the samples in the window (the caller decides the window by how often it samples), then `(soc − cutoff)/100 × capacity ÷ meanDraw × 60`, rounded to 10 minutes.

- [ ] **Step 4: Run tests to verify they pass**

Run: `sh tests/run.sh`
Expected: all assertions pass.

### Task 5: The screen

**Files:**
- Create: `src/app/SambokActivity.java`, `res/layout/activity_sambok.xml`, `res/values/strings.xml`, `AndroidManifest.xml`, `build.sh`

**Interfaces:**
- Consumes: `Car`, `Panel`, `Countdown`.
- Produces: an APK whose single Activity paints the panel and the dog scene.

- [ ] **Step 1: Build the layout at 8:3**

Panel on the left with temperature, countdown, toggle, status line; dog scene on the right; the amber strip across the top. Full-screen, status bar hidden, `FLAG_KEEP_SCREEN_ON`.

- [ ] **Step 2: Wire the state machine**

On create: read `Car.utilityOn()`; if on, show the scene with the toggle on; if off, show `off` with "tap to start". The toggle is a plain `Button` with `setOnClickListener` — a tap, not a press-and-hold. Enable path: set `starting`, call `Car.setUtilityOn(true)`, poll until on or 10 s, then scene or the generic failure line.

- [ ] **Step 3: Poll on a handler**

Every 5 s: read utility state, cabin temperature, unit, SOC, cutoff, draw → recompute → repaint. All reading happens off the main thread; a slow call must not freeze painting.

- [ ] **Step 4: Build the APK**

Run: `sh build.sh`
Expected: `aapt` compiles, `dx` produces `classes.dex` at API 19, APK is v1-signed, `aapt dump badging` shows only the permissions the app needs.
